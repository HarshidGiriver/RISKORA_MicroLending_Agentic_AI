## Data and representativeness

The generator samples borrower characteristics and creates labels from programmed relationships. Names in the demonstration queue and rows in the training CSV are not evidence of a real lending cohort. The dataset has no verified repayment timeline, real default observation window or independently measured collection process.

Synthetic data is useful for testing schema handling, model plumbing and the review workflow. Performance against labels created by the same generator does not establish accuracy on real applicants. A random split also does not test future economic periods, geographic transfer or deployment selection effects.

## Thresholds and human decisions

The configured thresholds are 8% and 20%. The metadata describes a 4:1 cost assumption; the project does not show a validated operational cost study or proof that 20% maximizes lending utility. Classification and approval are separate. Even a LOW case must pass input-quality checks and receive a recorded human decision before funding can be committed.

The display score is a piecewise transformation bounded to 5–99. It is not a CIBIL or other bureau score. Fractional funding changes lender concentration but must not change the borrower's predicted probability or band.

## Explanation and evidence limits

Policy indicators compare selected inputs with fixed thresholds and assign fixed points. Those points are not SHAP values, causal effects or a decomposition of the trained prediction. Their sum need not equal the display score. The global coefficient chart belongs to the logistic-regression baseline, not to the calibrated tree model.

ORA uses saved inputs and assessment results to make a deterministic evidence brief. Its SHA-256 digest identifies a normalized input snapshot; it does not certify that the supplied values are true. There are no bank, identity, psychometric or eNACH verification integrations. Dataset-explorer estimates are separate heuristics and must not be quoted as trained-model predictions.

## Missingness and safeguards

Creation requires eight fields; approval requires all 16 and acceptable internal consistency. Missing optional intake fields are retained as missing. Inference uses documented fallback values so an incomplete case can still produce a provisional assessment, but data-quality flags route it for verification. Users must not treat fallback values as supplied facts.

Startup validates the matching artifact set, feature count, class order and finite probability output. API validation rejects invalid ranges and categories. Saved assessments include an input snapshot, model version and reviewer reference. Human decisions refer to the latest assessment ID. These safeguards improve traceability; they do not validate real-world model fitness.

## Known limitations and release conditions

The model has no demonstrated fairness analysis, real-data calibration, independent test cohort, drift monitoring or production performance benchmark. Preprocessing is fitted on the outer training set before calibration folds; moving preprocessing inside cross-validation would improve fold isolation. The choice of final model is explicit in code rather than an automated selection procedure.

Before use for real lending, define the outcome and horizon, validate lawful data collection, evaluate representative historical outcomes, test temporal and subgroup behavior, compare against simple baselines, choose thresholds against actual costs and establish model review/rollback ownership. Keep the system in decision-support mode with human accountability.
